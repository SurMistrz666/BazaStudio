# Baza Studio Native

The desktop product is one native Rust application, Baza Studio. No WebView, Tauri, browser engine, localhost HTTP application, Python interpreter or Docker is required by the executable. Everything in this repository is free software under GPL-3.0-or-later (`../LICENSE`); dependencies and bundled assets keep their own licenses, listed in `THIRD-PARTY-NOTICES.txt`, `THIRD-PARTY-INVENTORY.json` and `third-party-licenses/`.

## Workspace organization

- `baza-core`: typed data and SQL, the engine registry and one database driver per engine family (`src/drivers/`, contract in `src/drivers/README.md`), SSH transport, encrypted OS vault, connection groups, optional local lock, release discovery on GitHub.
- `baza-studio`: the application (binary `BazaStudio`): native database workspace, connection editor with its SSH tab, SQL editor, result grid, data transfer, query builder and appearance preferences.
- `baza-qa`: acceptance tools without a window (binary `BazaQa`), built and tested with the workspace and never packaged; see "Acceptance tools" below.
- `scripts/`: OS-specific packaging; a package is accepted only after its engine and actual GPU-window checks pass.

## Interface contract

eframe/egui render native GPU windows; an owned Tokio multithread runtime runs database, SSH, file and update work off the UI thread. Bounded message channels deliver results. Rendering uses virtualized table rows; long-running work is cancellable. No CPU/GPU busy-loop while idle: repaint only on input, completed jobs and a bounded interval for live counters. A database engine exists in the application when its driver is listed in `drivers::REGISTRY`; an engine without a driver, its actions and its tests is omitted. The first three families are PostgreSQL, MariaDB/MySQL and SQLite, and the servers and services that speak their protocols are products of those families (see "Engines, products and drivers").

model.rs defines these serializable types; secrets do not derive Debug:

- `Engine`: a handle to the `EngineSpec` of an engine family, stored as the id of the family (`postgres`, `mysql`, `sqlite`, and the ids of later drivers). The ids never change. A profile that names an engine this build has no driver for still loads, is listed, cannot be connected and is saved back unchanged.
- `TlsMode::{Disable, Require, VerifyFull}`.
- `ConnectionProfile { id:Uuid, name:String, engine:Engine, host:String, port:u16, database:String, username:String, password:String, tls:TlsMode, ca_file:Option<PathBuf>, sqlite_path:Option<PathBuf>, color:[u8;3], ssh:Option<SshProfile>, product:String, options:BTreeMap<String,String> }`. `product` is the id of the product of the family the connection was made for (`amazon-aurora-postgresql`); it is empty for the generic product. `options` holds the engine's own connection fields by their key, never a secret. Both are written only when set, so a profile of an earlier version is read and written back byte for byte; exported profile files (plain and BZX1) carry them the same way.
- `SshAuth::{Password, PrivateKey}`.
- `SshProfile { host:String, port:u16, username:String, auth:SshAuth, password:Option<String>, private_key:Option<String>, passphrase:Option<String>, fingerprint:String }`.
- `TunnelProfile { id:Uuid, name:String, ssh:SshProfile, target_host:String, target_port:u16, local_port:u16 }`.
- `Preferences`: PL/EN, five dark themes (default VS Code), interface size and accent, density, striped grid, SQL line numbers and wrapping, and optional local SQL copies. Older records receive compatible defaults for newly added fields.
- `ProfileSet { version:u32=1, connections:Vec<ConnectionProfile>, tunnels:Vec<TunnelProfile>, preferences:Preferences }`. `tunnels` and `TunnelProfile` stay in the stored format so that vaults and exported bundles holding tunnel entries keep loading; a tunnel that is actually opened is described by the `ssh` field of a connection.
- `HistoryRecord { id:Uuid, connection_id:Uuid, sql:String, status:String, started_at:String, duration_ms:u64, rows:u64, error:Option<String> }`.

Vault API: `Vault::open_default(application:&str)->Result<Vault>` (accepts only `BazaStudio`) and `Vault::open_owned(path:&Path,namespace:&str)` for owned QA fixtures; `load_profiles()->Result<ProfileSet>`, `save_profiles(&ProfileSet)`, `append_history(&HistoryRecord)`, `load_history()->Result<Vec<HistoryRecord>>`, `clear_history()->Result<usize>` (replaces the history with an empty record in one atomic write and removes the opt-in plain SQL copies of the same runs); standard error results with fixed safe summaries and no raw credentials. Key material is held in zeroizing buffers. The application owns a private data directory and key namespace per current OS user. Windows DPAPI current user. On macOS the key is a generic password in the user's login keychain, written and read through `/usr/bin/security` (account `native-master-v2`): an item made by the application itself is bound to that exact build by the keychain partition list, so every ad-hoc signed update would stop at a system prompt. Any process of the same user can therefore obtain the key, the same model as DPAPI. A vault that only holds the key of an older build (`native-master-v1`) is opened once through the system prompt when it contains user data, and is started clean without reading the old key when it does not. On macOS the lock of a vault is a file per scope in `~/Library/Application Support/BazaNativeLocks`. That folder is checked for being private without opening the lock files of other vaults (the vault's own folder is still checked with everything below it), and a QA scope removes its lock file together with its key, so tests and self-tests do not pile files up there. Authenticated encryption AES256-GCM binds record context/version; atomic publication, no plaintext secret fallback, no insecure permissions repair of existing files, no partial first key. Local SQL copies only after explicit opt-in, sanitized filename and credential-redacted SQL. Native profiles import/export has preview/selection/corrections, no silent imported secrets, explicit encrypted portable export with passphrase and secrets option.

SSH API: async `TunnelManager::new()`, `start(&TunnelProfile)->Result<TunnelStatus>`, `stop(Uuid)->Result<TunnelStatus>`, `status(Uuid)->Option<TunnelStatus>`, `statuses()->Vec<TunnelStatus>`, `shutdown()`. Clonable shared manager; the server host key is checked before any credential is sent (see below); trusted manually configured local desktop gateway hosts permitted. Listener only on 127.0.0.1, local port 0 or >= 1024, at most 8 tunnels, 32 forwarded connections per tunnel and 256 per manager. Connecting and the handshake are bounded and cancellable; a running tunnel has no idle timeout and stays up until it is stopped or SSH keepalives show that the gateway is gone. Each forwarded connection copies its two directions independently, so a half-closed client still receives the whole answer. `TunnelStatus { id:Uuid,state:String,local_port:Option<u16>,bytes_sent:u64,bytes_received:u64,active_clients:u32,error:Option<String>,host_key:Option<HostKeyScan> }`; `state` is `starting`, `active`, `stopping`, `stopped`, `failed` or `disconnected`, and `error` is a stable code. While a tunnel is `active`, `error` names why the latest forwarded connection could not be opened (for example `tunnel_target_refused`).

Host key trust works like an ordinary SSH client, so nobody has to type a fingerprint. `SshProfile.fingerprint` is optional. Empty means "not trusted yet": the first connection accepts the key the server proves (never a host certificate, RSA only from 2048 bits) and reports it in `TunnelStatus.host_key`; the application saves that fingerprint into the profile straight away. A non-empty fingerprint is a strict pin. When the server presents another key the connection fails before any credential is sent, with the code `ssh_host_key_changed`; the new key is available both as `TunnelStatus.host_key` of the failed tunnel and as the typed error `ssh::HostKeyChanged { presented }` (`error.downcast_ref()`), so the interface can warn and offer an explicit "trust the new key" action. A saved fingerprint is never replaced automatically. Profiles saved by earlier versions keep their pin; the stored format is unchanged.

`ssh::scan_host_key(host, port) -> Result<HostKeyScan { fingerprint, algorithm }>` connects, reads the host key the server proves during key exchange and disconnects before any authentication. It applies the same key policy as a pinned connection (no host certificates, RSA of at least 2048 bits) and returns the fingerprint in the exact `SHA256:…` form a profile stores. It backs the optional "fetch from server" button in the advanced part of the SSH tab, for people who were given a fingerprint to compare; a scan cannot tell a genuine server from an intercepted connection. When a saved fingerprint does not match the first key a server presents, the remaining host key types (Ed25519, ECDSA, RSA) are requested before `ssh_host_key_changed` is reported, because an administrator may hand out the fingerprint of any of the server's keys.

Every `ssh_*`, `tunnel_*` and `local_port_*` code has a short Polish and English sentence in `ssh::describe(code, en)`; `ssh::describe_known` returns `None` for codes that belong to other modules. The codes tell apart, among others, DNS failure, refused connection, connect timeout, a service that is not SSH, a changed host key, unsupported algorithms, a sign-in method the server does not offer, rejected password or key, private key problems, a local port in use and a target the gateway cannot reach. `crates/baza-core/tests/real_sshd.rs` is an ignored end-to-end test that runs these paths against a real SSH server described by `BAZA_SSH_TEST_*` variables.

There is no separate tunnel application. A tunnel is configured in one place only, the SSH tab of a database connection: host, port, user name and a password or a private key with its passphrase. When such a connection is opened, Baza Studio builds a `TunnelProfile` from the connection's `ssh` settings, starts it on a `TunnelManager` owned by that connection, in-process, and lets the database driver dial the loopback listener; the tunnel is shut down with the connection. The server key is trusted on first use as described above, and the fingerprint learned on the first connection is saved into the connection profile. Saving the connection editor never replaces that key by accident (`connection_edit::server_key_to_save`): a fingerprint field the user did not touch keeps the saved key, even when the editor was opened before the key was learned. The key goes only when the user changes or clears the field in the advanced part of the SSH tab, or when the SSH host or port is no longer the saved one, because the key belonged to another server. "Test połączenia" runs with the same key the save would store.

Both "connect" and "Test połączenia" go through one function, `connection_edit::open` in `baza-studio`: it starts the tunnel, lets the driver dial it and, on any failure, closes the tunnel again; when the driver fails behind a tunnel, the reason the tunnel knows (for example `tunnel_target_refused`) is reported instead of the driver's network error. `Database::connect` gives the failures a person can act on codes of their own: `database_login_rejected`, `database_not_found`, `database_access_denied`, `database_certificate_rejected` (a certificate that does not pass verification, such as the self-signed one current MariaDB servers present by default) and `database_tls_unsupported`. The ignored test `connection_edit::over_ssh` runs this path against a real SSH server and a real MariaDB/MySQL or PostgreSQL behind it, described by `BAZA_SSH_TEST_*` and `BAZA_DB_TEST_*` variables: key sign-in, trust on first use, reconnect with the saved key, a changed key, a wrong database password, a closed database port and the end of the tunnel on disconnect.

## SQL text

`sql::statements(dialect, text)` and `sql::editable_table(dialect, text, tables)` read quotes and comments the way the engine of the dialect does, because the engines disagree on where a string literal ends: MySQL and MariaDB treat a backslash inside `'…'` and `"…"` as an escape and `"…"` as a string, PostgreSQL only inside `E'…'` (and has `$tag$…$tag$` bodies and nested comments), SQLite never. A file opened into the editor is accepted when any registered SQL dialect reads it to its end (`sql::check_script`). Generated `LIKE` filters escape `%`, `_` and the escape character itself with `!` (`sql::LIKE_ESCAPE`, `ESCAPE '!'`), never with a backslash; on PostgreSQL the filter is `CAST(column AS TEXT) ILIKE …`, so that numbers are searched as text and letter case is ignored as in the other two engines; TiDB, whose default collation compares bytes, gets `LOWER(column) LIKE LOWER(…)`. A MySQL text literal is written `_utf8mb4 0x…`: like `CONVERT(0x… USING utf8mb4)` it keeps quotes and backslashes of the value away from the parser, but it is a literal, so it takes the collation of the column it is compared with (MySQL 8 refuses the `CONVERT` form against a column of any collation but the default one). A filtered table therefore stays one statement on one known table and keeps single-cell editing. `crates/baza-core/tests/real_database.rs` checks the filters and an edit of a filtered row on SQLite with every test run and, ignored by default, on a real MariaDB/MySQL or PostgreSQL server.

## Engines, products and drivers

Nothing outside `crates/baza-core/src/drivers/` asks which engine a connection is. An engine family is one module there with a static `EngineSpec`: the form of the connection dialog (`ConnectionForm`, plus the engine's own `OptionField`s), what the interface may offer (`Capabilities`: SQL editor or command console, schemas, filter and sort, cell editing, row insert and delete, table designer, query builder, import, export, monitor, and whether tables, document collections or keys are browsed), how its SQL is written (`Dialect`: name quotes, literals, paging, the contains filter, the lexer rules) and its products. The modules are listed once, in `engines!` of `drivers/mod.rs`; `drivers::REGISTRY` is that list.

A product is a preset of a family: label, picker group, a painted badge, default port, TLS mode, database and user name, and its own dialect or capabilities where it differs (Amazon Redshift, TiDB). The connection dialog picks a product from a grouped, searchable list; choosing one applies its defaults where the draft still holds the defaults of the previous product. Where servers of one family differ in something a driver does (catalogs, stopping a statement, literals), the driver asks the server what it is after connecting, so a profile of the generic product works against any server of the family.

An open connection is a `drivers::Session` trait object behind the `database::Database` facade: run a statement or a command with cancellation into a typed `QueryResult`, list containers, describe columns, read a page (`PageRequest`), make one change of one record with the conflict check (`RowChange`), bulk import, server statistics, close. A driver with SQL implements the statement level and gets pages and changes from its dialect; a driver without SQL overrides them. "Dane tabeli" reads pages and applies changes through these operations for every engine. A driver is given the address to dial (the real host, or the loopback end of an SSH tunnel) separately from the server name used for TLS.

`crates/baza-core/src/drivers/README.md` is the contract for adding an engine: the files a driver may touch, the trait, the descriptor, how capabilities change the interface, and the table of what each product was verified against. `tests/driver_checklist.rs` is the live checklist every SQL server passes.

## Distribution

Separate real MSVC Windows x64, Apple Silicon and Intel macOS builds. Pinned Cargo.lock and dependency/license audit. `--self-test --report <file>` performs own temporary-data tests against actual OS vault and real local SQLite, with source/version/provenance; native renderer acceptance is separate from headless tests. `--native-ui-self-test --report <file>` is that renderer acceptance: it opens the real window on an owned temporary vault and a sample SQLite file, above the other windows and without taking the keyboard, and saves a screenshot next to the report. Its `--qa-*` switches (view, language, theme, size, pixel density, scripted input with intermediate screenshots) are documented at the top of `crates/baza-studio/src/app/qa.rs` and are ignored by a normal launch. A run that the system never paints is ended by a watchdog with `native_window_not_painted`. Binary acceptance measures cold start, UI responsiveness, large result scrolling and idle use without claiming measured performance from source. Windows `.exe`, native Mac `.app/.dmg`. `BazaStudio` is the only packaged program.

The application needs no account and no online service to work. The only request it makes on its own behalf is the manual update check: an anonymous `GET https://api.github.com/repos/SurMistrz666/BazaStudio/releases`, without a token, cookies or any installation identifier. `Updater::check()` returns `UpdateCheck::{Available(UpdateOffer), UpToDate, Unreachable}`: the newest non-draft release whose tag is a semantic version above the running one is offered; 404 (nothing published) is `UpToDate`; a network failure, a rate limit or any other refusal is the quiet `Unreachable` state; `Err` is kept for an answer that is not a list of releases of this repository, explained by `updater::describe(code, en)`.

Packages are not downloaded or started by the application. An offer shows the version, the release notes, and the size and SHA256 GitHub reports for the package of this system; `UpdateOffer::open_page()` opens the release page in the browser and `UpdateOffer::matches_file(path)` compares a downloaded file with that size and SHA256. Only pages inside `https://github.com/SurMistrz666/BazaStudio` can be opened (`updater::open_project_url`).

Vaults written by earlier previews may contain two records that nothing reads any more (`RETIRED` in `vault.rs`). They are removed when the vault is opened and never count as evidence of an initialised vault.

## Connection groups

Groups are a separate encrypted record, not additional fields in imported connection profiles. UUID membership and parent relationships are validated before an atomic compare-and-swap update. Limits are 256 groups, eight nesting levels and 1,000 memberships. Sibling names are case-insensitively unique; cyclic or orphaned hierarchies are refused. Removing a group promotes its children and releases its connection memberships without deleting any connection. A conflicting promoted name leaves the whole record unchanged.

## Database TLS over SSH

The two SQLx 0.9.0 network drivers have a narrow, documented TCP-destination extension in `vendor/`. The TCP socket can use an owned loopback SSH listener while the original database hostname remains the certificate/SNI identity. No certificate verifier or authentication protocol is replaced. Original archive hashes, licenses and the exact four-file patch are retained. Both actual TLS database fixtures and certificate-rejection cases must pass before distribution (`BazaQa --tls-self-test`).

## Acceptance tools

`crates/baza-qa` builds `BazaQa`, a command-line program without a window. It is a workspace member, so `cargo build`, `cargo test` and `cargo clippy` cover it, but the packaging scripts never copy it. It never opens the application's vault: the vault tools call `Vault::open_owned` on a directory of their own under the temporary directory, in a `BazaStudio.QA.` key namespace, and remove both when they finish.

- `BazaQa --tls-self-test --fixture <file> --report <file>` connects to caller-owned PostgreSQL and MariaDB test servers through loopback SSH forwards with full certificate verification. For each engine it checks an encrypted session, exact round trips of large integers, decimals, binary and JSON values, a single-cell update with its optimistic guard, refusal of a certificate for another name and of an untrusted issuer, and that a verified connection still works afterwards. The fixture file names the forwarded ports, the test account and the CA file; only tables created by the run are changed and dropped.
- `BazaQa --vault-concurrency-worker --qa-run <uuid> --report <file>` is started several times at once with the same UUID. Every process opens the same new vault, so exactly one of them may create the key, and each adds one to a shared counter.
- `BazaQa --vault-concurrency-finalize --qa-run <uuid> --expected-workers <count> --report <file>` checks that the counter equals the number of workers and that no temporary file was left behind, then removes the QA vault and its key.
